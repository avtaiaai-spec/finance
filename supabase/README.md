# Подключение личного кабинета

## 1. Настройка базы

В проекте Supabase откройте **SQL Editor → New query**, вставьте весь `setup.sql` и нажмите **Run**. Подтвердите предупреждение редактора только для этого скрипта. Он создаёт собственные таблицы и заменяет только свои политики, не очищая финансовые записи. Повторное выполнение допускается. В результате должно появиться **Success**.

Скрипт предоставляет пользователю SELECT только на его строки. Запись выполняется через функцию с проверкой `auth.uid()` и ожидаемой версии; напрямую вставлять или менять таблицы через браузер нельзя. `finance_history` сохраняет предыдущую версию перед изменением; версии старше 30 дней очищаются при следующих записях владельца. Приватные и административные ключи для сайта не нужны.

## 2. Ссылки авторизации

Откройте **Authentication → URL Configuration**:

- **Site URL:** `https://avtaiaai-spec.github.io/finance/`
- **Redirect URLs:** добавьте точный адрес `https://avtaiaai-spec.github.io/finance/`

Сохраните изменения. Email-провайдер должен быть включён. Подтверждение адреса рекомендуется оставлять включённым. Письма регистрации и восстановления отправляет Supabase; ограничения встроенной почты и необходимость своего SMTP проверяются в настройках проекта при проблемах доставки. Не публикуйте пароль SMTP, пароль БД или secret/service_role ключи.

## 3. Первое использование

1. Сначала скачайте JSON-копию на устройстве с наиболее полной историей.
2. Откройте сайт → **Настройки → Личный кабинет → Регистрация**. Это новый аккаунт приложения; учётная запись панели Supabase автоматически его не создаёт.
3. Подтвердите почту по письму и войдите в приложение.
4. В пустом облачном аккаунте на основном устройстве выберите **Перенести мои данные в облако** и проверьте количества записей. Только после подтверждения начнётся перенос. Исходная гостевая история остаётся отдельной локальной копией.
5. Дождитесь статуса **Все изменения в облаке**.
6. На другом устройстве войдите в тот же аккаунт. Повторно импортировать CSV и переносить старую локальную копию не нужно.

Синхронизация проверяет версию примерно раз в 12 секунд, при возвращении к приложению и восстановлении сети. Полные данные загружаются только при новой версии. Кнопка «Синхронизировать» запускает проверку сразу. Изменения сначала записываются в локальную очередь; при потере связи уже открытое приложение продолжает работать с данными действующей сессии. Холодный запуск полностью без сети не реализован: service worker отсутствует.

Независимые изменения объединяются по идентификаторам и полям, удаления учитываются. Повторные записи одной CSV-строки распознаются по метке импорта. Одновременное изменение одного поля требует выбора в кабинете. Если нарушаются связи между категориями и операциями, потребуется выбрать полную версию. Перед разрешением спора можно скачать свою JSON-копию. Облачная предыдущая версия сохраняется функцией записи. При восстановлении полной истории из JSON или облачной версии изменения распространяются на все устройства аккаунта.

История восстановления находится в **Личный кабинет → Восстановление из облачной истории**. Это восстановление всей версии, а не отдельная корзина каждой операции. Проверьте количество операций и скачайте текущую копию перед заменой.

После выхода интерфейс переключается на исходную локальную историю. Кэш аккаунта и очередь сохраняются на этом браузере, чтобы не потерять несинхронизированные правки. На общедоступном устройстве не оставляйте сеанс открытым; локальная копия не защищена от человека с доступом к самому браузеру. Выход не удаляет облако.

## Проверки

`npm test` включает финансовые расчёты, конфликты, автономную очередь, потерянный ответ, SQL и RLS. SQL проверяется локально реальным PostgreSQL-движком PGlite с двумя ролями пользователей. `tests/browser_cloud.py` использует настоящий клиент Supabase с перехваченным тестовым сервером для входа, двух устройств, миграции, офлайна, восстановления и смены аккаунта. Эти тесты не доказывают готовность живого Supabase-проекта: необходимы успешный SQL, ссылки авторизации, реальная регистрация, доставка письма и проверка на двух устройствах.

Для прямой диагностики из рабочей среды нужен сетевой доступ к `dshtycqngfqqvnensvlb.supabase.co`. Публичный ключ и URL в `src/cloud-config.ts` предназначены для браузера; доступ к данным защищается аутентификацией и RLS, а не сокрытием publishable key.

В одном браузере редактирование одного аккаунта разрешено только в одной вкладке одновременно (Web Locks). Вторая вкладка покажет подсказку и автоматически продолжит работу после закрытия первой. Это защищает общую локальную очередь при отсутствии сети. Дата последнего ручного расхода хранится отдельно на каждом устройстве: работа с другой датой на компьютере не сбрасывает дату пакетного ввода на телефоне.

## Имя и фото профиля

Для фото один раз выполните `supabase/profile.sql` в SQL Editor. Скрипт создаёт закрытый bucket `finance-avatars` и политики доступа только к папке текущего `auth.uid()`. Глобальные права Storage и финансовые таблицы не меняются. Новые фото загружаются под уникальными именами; запись существующего файла не используется. Только JPEG до 1 МиБ разрешён на стороне bucket.

В приложении: **Настройки → Личный кабинет → Мой профиль**. Имя хранится в собственном `auth.user_metadata.display_name`, путь фото — в `avatar_path`. Эти поля служат оформлению, а не проверке прав: доступ определяется JWT и RLS. Профиль доступен на устройствах одного аккаунта. Метаданные перечитываются при возвращении к приложению и примерно раз в минуту. Фото показывается по временной подписанной ссылке сроком на час; ссылка обновляется при возвращении и каждые 45 минут. Подписанную ссылку не следует публиковать.

Выбранное фото сначала обрабатывается на устройстве: центрируется, обрезается в квадрат, уменьшается до 512×512 и заново кодируется JPEG без исходных метаданных. Допустимы JPEG, PNG, WebP до 10 МБ и 60 Мп. HEIC при необходимости нужно преобразовать в JPEG. До «Сохранить профиль» файл не загружается. Замена сначала загружает новый файл, затем меняет профиль и удаляет предыдущий файл. При ошибке обновления новый файл удаляется только после проверки, что профиль на него не ссылается. При сбое сети возможны неиспользуемые закрытые файлы; финансовые данные от сохранения профиля не меняются.

Имя и изображение находятся в Auth/Storage, отдельно от JSON-копии финансов. SQL-политики проверяются в `src/profile-sql.test.ts` на PostgreSQL. `python tests/browser_profile.py` проверяет реальный SDK с тестовым сервером: сохранение, фото, конвертацию, две сессии, замену, удаление и ошибки. Живое хранилище требует успешного выполнения `profile.sql` в вашем проекте.
